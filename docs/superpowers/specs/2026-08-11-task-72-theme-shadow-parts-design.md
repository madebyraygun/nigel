# Task 72 — Dialogs and form fields render unpainted: the theme has to reach inside the shadow roots

Stream 4 (Web theme), PR-4a. First of three: TASK-72, then TASK-75 (mode
switcher), then TASK-76 (mono typeface). The other two both depend on this one
— a mode switcher is a `wa-radio-group` inside a `wc-*` shadow root, and a
print check is worthless while the print sheet cannot reach the chrome it
claims to hide.

**Objective:** the theme's `wa-*` treatment actually applies. Dialogs paint an
opaque panel, form fields carry field chrome, and the mechanism is one a new
component cannot silently opt out of.

---

## 1. Where the codebase actually is

Surveyed before writing this; these are the load-bearing facts.

**The theme is loaded exactly once, at document level.**
`web/apps/app/src/main.ts` is three lines, the first of which is
`import '@nigel/theme/css/nigel.css'`. That file is generated by
`web/packages/theme/scripts/build-css.js` from `nigelTheme`
(`web/packages/theme/src/themes/nigel.ts`), which composes seven token modules,
`globalCss` (`web/packages/theme/src/global.ts`) and `printCss`
(`web/packages/theme/src/print.ts`). The preview harness loads the same file
(`web/packages/ui/preview/main.ts`).

**Every component in the product has a shadow root.** `LitElement` opens one by
default and nothing overrides it — `rg -n "createRenderRoot" web/` returns
nothing, in `packages/ui`, in `apps/app`, and in `preview/`. `nigel-app`
(`web/apps/app/src/components/nigel-app.ts`) is the only element in the
document; `wc-app-shell` and every screen live inside its shadow root, and every
`wa-*` primitive lives one level deeper still.

**`::part()` crosses exactly one boundary, from the tree the rule is in.** A
document-level rule can style parts of an element that is *in the document*.
`wa-dialog` is inside `wc-manager-dialog`'s shadow root, which is inside a
screen's shadow root, which is inside `nigel-app`'s. The document sheet cannot
even select `wa-dialog`, let alone its parts.

**So the whole of `global.ts` is dead, not only the dialog and field rules.**
The task names `wa-dialog::part(header|body|footer)` and
`wa-input|wa-select|wa-textarea::part(base)`. The same argument condemns the
rest of the file:

| Rule in `global.ts` | Intended effect | Status today |
|---|---|---|
| `wa-button[variant=brand]::part(base)` | the brand gradient on every primary button | never matches |
| `wa-button:hover/active::part(base)` | hover and press treatment | never matches |
| `wa-button::part(label)` | button type treatment | never matches |
| `wa-*::part(form-control-label)` | field label type and colour | never matches |
| `wa-input/select/textarea::part(base)` | field surface, border, radius | never matches |
| `wa-dialog::part(header/body/footer)` | opaque dialog panel | never matches |
| `:focus-visible` | the 2px brand focus ring | never matches anything inside a component |

Every visible button in the app is a Web Awesome default. That is the same bug,
reported once.

**`print.ts` is half dead for the same reason.** Its token repainting works —
custom properties inherit through shadow boundaries, which is exactly why the
file says so in its own comment. Everything else in it does not:

- `wc-app-shell::part(sidebar|header|banner|content)` — `wc-app-shell` is inside
  `nigel-app`'s shadow root, so the document sheet cannot select it.
- `wc-nav-sidebar, wc-toast, wc-export-links, wc-period-nav,
  wc-register-toolbar, wa-button, wa-select, [data-print='hide']` — all of them
  live inside shadow roots too.

`web/packages/theme/__tests__/print.test.ts` asserts that those selectors are
*present in the stylesheet text*, which they are. Nothing asserts that they
match anything. `web/README.md` carries a manual print checklist ("No sidebar,
header, banner, period control or export buttons") — either it has not been
walked since the shell moved inside `nigel-app`, or it was walked and the
sidebar was read as intentional. Printing today gives black-on-white tokens with
the full application chrome still on the page. **Verify this in a browser before
writing the fix** (see plan Task 1.1); the reasoning is sound but it is a
prediction, not an observation.

**`nigelTheme` has no component consumers.** `rg "nigelTheme"` finds the theme
package itself, its four tests, and `build-css.js`. No `static styles` anywhere
adopts it. `web/packages/ui/src/components/wc-invoice-status.ts` mentions
`@nigel/theme` in a comment only.

only `wc-*` element that is ever a document child. It does not help: `wc-confirm`
is in the document, but its `wa-dialog` is inside *its* shadow root, so the
document sheet still cannot reach the parts.

**Why the app looks half-right.** Colour, type, spacing and radius all come from
custom properties defined at `:root`, and custom properties inherit through
shadow boundaries. That is the one channel that works, which is why the task
reports "colour and type look correct while the surfaces do not".

## 2. Candidate mechanisms, honestly

### A. `exportparts` chains — rejected

`wa-dialog` would need `exportparts="header,body,footer"`, `wc-manager-dialog`
would need to re-export them, the screen would need to re-export those, and
`nigel-app` would need to re-export those. Four hops for one dialog. Part names
collide across siblings (`wc-account-form` and `wc-rule-form` both expose an
input `base`), so every hop needs renaming (`exportparts="base:account-name-base"`),
and the document sheet then has to name every renamed part explicitly. Every new
component adds a link to every chain above it, and nothing fails when someone
forgets. This is the mechanism the platform offers for *deliberately* publishing
one or two parts of a leaf component upward, not for theming forty of them.

### B. Adopt the whole `nigelTheme` into every shadow root — rejected

This is what the task's phrasing points at ("nigelTheme, the CSSResult a
component would adopt"), and it does work for the part overrides. The problems
are that most of what it carries is inert or wrong inside a shadow root:

- `:root { … }` matches nothing inside a shadow root — the root there is
  `:host`. So every token declaration in the adopted copy is dead text; the
  tokens the component actually reads still come from the document sheet by
  inheritance.
- `@media print { :root { … } }` is dead for the same reason, so the adopted
  copy does not carry print's recolouring either.
- `print.ts`'s `wc-app-shell::part(sidebar)` is meaningful in exactly one
  shadow root (`nigel-app`'s) and meaningless in the other forty.
- It is not a memory problem — Lit caches one `CSSStyleSheet` per `CSSResult`
  and `adoptedStyleSheets` shares it — but it is a comprehension problem. A
  reader opening `wc-client-form` in devtools sees the entire design system
  inlined into the field wrapper, 90% of which cannot match.

Adopting a sheet whose majority is inert teaches the next person that adopting
sheets is how tokens get in, which is the misunderstanding that produced this
bug.

### C. A dedicated part-override sheet, adopted where `wa-*` is rendered — **recommended**

Split `global.ts` in two by audience rather than by topic:

- what only works at **document** level (nothing, once the part rules leave —
  the document sheet becomes tokens + dark + print);
- what only works **inside a shadow root** (the `wa-*` part overrides and the
  focus ring), exported as `controlsCss` and adopted by the twenty-three files
  that render a primitive.

Each component's `static styles` becomes `[controlsCss, css\`…\`]`. Its own
rules come after, so a component can still override the shared treatment, and
the shared treatment is one object shared by every adopter.

A **guard test** (§3.4) fails the build when a file imports a
`@awesome.me/webawesome/dist/components/…` module without adopting the sheet.
That is what makes this different from "remember to add the import": it is the
same enforcement shape as `apps/app/src/__tests__/api-seam.test.ts`, which is
already the repo's answer to "a convention the next screen can forget".

### D. A themed base class or mixin — rejected as the primary, kept as a fallback

`class WcThemedElement extends LitElement { static styles = [controlsCss] }`,
or `WithControls(LitElement)`. Tempting, and it is less repetitive than C.
Against it:

- The inheritance slot is already contended. `packages/ui/src/icons/` has
  `WcIconBase`, and every screen element in the app is
  `SignalWatcher(LitElement)`. A base class means either a second base
  (`WcThemedIconBase`) or a mixin, and a mixin is C plus indirection.
- Subclassing must not silently drop the sheet. `static styles` in a subclass
  *replaces* the parent's unless the author writes `[...super.styles, …]` — a
  footgun that produces exactly the symptom this task is fixing, in a form that
  is harder to see.
- It adds the sheet to the forty components that render no `wa-*` at all, so
  "which components depend on the primitive treatment" stops being answerable
  from the source.
- It needs the same guard test anyway, because the app's screens would have to
  remember to extend it.

If review prefers D, the plan's Task 3 changes shape and nothing else does: the
sheet, the split and the guard test are the same.

**Recommendation: C.**

## 3. The design

### 3.1 `@nigel/theme` splits `global.ts`

`web/packages/theme/src/global.ts` keeps its rules and changes its export name
and its doc comment, both of which currently state the opposite of the truth
("`::part()` pierces the shadow DOM but only from a document-level stylesheet"
— it is the other way round for a component tree of this shape).

```ts
// web/packages/theme/src/global.ts  →  renamed to src/controls.ts
export const controlsCss = css` … the seven rule groups, unchanged … `;
```

The rules themselves do not change. They were always correct; they were in the
wrong tree.

`src/index.ts` exports `controlsCss` and stops exporting `globalCss`. Nothing
outside the package imports `globalCss` today, so this breaks no consumer.

### 3.2 `nigelTheme` keeps its name and loses what it cannot deliver

```ts
export const nigelTheme = css`
  ${colorCss} ${typographyCss} ${spacingCss} ${gradientCss}
  ${radiusCss} ${shadowCss} ${motionCss} ${colorDarkCss} ${printCss}
`;
```

`controlsCss` is **not** in it. A document sheet carrying rules that cannot
match anything is precisely what AC #5 objects to.

AC #5 is then satisfied by the first of its two branches, not the second:
`nigelTheme` keeps a real consumer — `build-css.js`, which turns it into
`dist/css/nigel.css`, which `main.ts` and the preview harness load. Its job is
and always was "the document-level sheet". Deleting the export would mean
deleting the document sheet.

`__tests__/nigel-theme.test.ts` currently asserts the composed sheet "carries
the global wa-* shadow-part overrides" and that the light/dark/parts ordering
holds. Those three assertions move to a new `controls.test.ts` and the ordering
assertion narrows to light-before-dark-before-print.

### 3.3 `print.ts` stops trying to reach across the boundary

The token repainting stays exactly where it is — it is the part that works.
The chrome hiding moves into the components that own the chrome:

| Today, in `print.ts` (dead) | Moves to |
|---|---|
| `wc-app-shell::part(sidebar/header/banner)` `display: none` | `wc-app-shell`'s own `@media print` block: `header, .banner { display: none }` and `::slotted([slot='sidebar']) { display: none }` |
| `wc-app-shell::part(content)` `padding: 0; overflow: visible` | the same block, on `.content` |
| `wc-nav-sidebar, wc-toast, wc-export-links, wc-period-nav, wc-register-toolbar` `display: none` | each component's own `@media print { :host { display: none } }` |
| `wa-button, wa-select` `display: none` | `controlsCss`'s own `@media print` block — it is adopted into every root that has one |
| `[data-print='hide']` | keep in `print.ts` **and** add it to `controlsCss`, so both trees honour it |
| `thead`, `tr`, `a`, `break-inside` | keep in `print.ts` for document-level content, and add the same rules to `controlsCss` so tables inside components get them |

The parts on `wc-app-shell` stay exposed. They are cheap, they are documented,
and `nigel-app` — which *is* one boundary away from the shell — can still use
them if a future need appears.

This is a scope addition beyond the task's text. It is the same root cause and
the same fix, it is a prerequisite for TASK-75's "print must keep winning" AC
being checkable at all, and leaving it would mean shipping a second known-dead
set of rules right after removing the first. **Flagged for Sam in §7.**

### 3.4 The guard test

Two files, one per package, both pure source scans (node environment, no DOM):

- `web/packages/ui/src/__tests__/controls-adoption.test.ts`
- `web/apps/app/src/__tests__/controls-adoption.test.ts`

Each walks its `src` tree, and for every `.ts` file that is not a test or a
preview and that contains `@awesome.me/webawesome/dist/components/`, asserts the
file also contains `controlsCss` (both the import and a use inside
`static styles`). The failure message names the file and says what to add.

The rule is deliberately blunt — `wc-dropzone` only renders `wa-format-bytes`,
which exposes no part we style, and it will be required to adopt the sheet
anyway. An exemption list is a place for the next component to hide.

### 3.5 What lands where

```ts
// every affected component
import { controlsCss } from '@nigel/theme';

static styles = [controlsCss, css` … existing rules unchanged … `];
```

`@nigel/theme` is already a `devDependency` of `@nigel/ui` and a `dependency` of
`@nigel/app`, and `apps/app/src/__tests__/dependency-manifest.test.ts` already
enforces that. No manifest change is needed.

One cascade note, because it is the thing most likely to be doubted in review:
for normal declarations, a `::part()` rule written in the **outer** tree wins
over the shadow tree's own rules for the same property, regardless of
specificity. That is what makes `controlsCss` able to repaint Web Awesome's
internals from `wc-manager-dialog`'s root at all, and it is why the sheet must
be adopted by the component that *hosts* the primitive rather than by some
ancestor.

### 3.6 What this does not do

- It does not restyle anything. Every declaration is the one already written in
  `global.ts`; the only thing that changes is which tree it lives in. If a
  surface looks wrong after this lands, the rule was wrong all along and that is
  a separate change.
- It does not touch tokens. Tokens already work.
- It does not add a component. `wc-manager-dialog` and `wc-client-form` gain a
  line each.

On AC #6, one honesty note: axe under jsdom does not evaluate colour contrast
(it needs layout and painted colour), so `describePreviewA11y` proves the new
state is structurally sound, not that the panel is opaque. Opacity is proved by
the rule-presence assertion and by eyes on the harness at :9090. Saying so here
so nobody later reads a green axe run as proof of the fix.

## 7. Open questions for Sam

1. **Is the print-chrome relocation (§3.3) in scope for PR-4a?** It is the same
   root cause and the same fix, and TASK-75's print AC cannot be checked
   honestly without it. It also grows the diff by about eight components. The
   alternative is a fourth PR, or folding it into 4b where the print AC lives.
   Recommendation: in 4a.

2. **Rename `globalCss` → `controlsCss`, or keep the name?** Keeping it means
   the file's name keeps saying "global" about a sheet that is now
   deliberately local to shadow roots. Renaming touches `index.ts` and four
   tests and nothing else.

3. **Should the focus ring be in `controlsCss` or in every component?** It is in
   `global.ts` today as a bare `:focus-visible`, so adopting it puts a focus
   ring on every focusable inside every adopting root — which is what we want,
   but it also means components that render no `wa-*` (and so do not adopt the
   sheet) keep the browser default ring. Options: leave the asymmetry, or split
   a two-line `focusCss` that every component adopts. Recommendation: leave it
   for now and revisit if a bare-`button` component looks wrong in the harness.

4. **How much of Web Awesome's default treatment do we actually want back?**
   Once `wa-button[variant=brand]::part(base)` starts matching, every primary
   button in the app changes appearance for the first time — the brand gradient
   has never rendered. That is the intended design, but it is a visible change
   nobody has seen. Worth a look at the harness before the browser pass on the
   app.
